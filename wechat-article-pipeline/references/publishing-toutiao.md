# 今日头条 Computer Use 操作 Chrome 发布流程

仅在用户明确要求同步、保存草稿或发布今日头条时使用本流程。复用用户真实 Chrome 中已有的登录态，**从头到尾只使用 Computer Use 操作和读取 Chrome**。工作台格式选择、复制、地址栏导航、头条页面检查、标题与正文填写、选项设置、提交和结果核验都必须通过 Computer Use 完成。

此流程禁止初始化或调用 Browser/Chrome browser automation；禁止使用 browser-client、`agent.browsers`、Playwright、CDP、DOM evaluation、`tabs.new()`、`tab.goto()` 或任何后台标签页对象。不要把自动化标签页的 URL、截图、焦点或 DOM 当成真实 Chrome 前台证据。微信草稿箱的“只用官方 API”限制只适用于 `mp.weixin.qq.com`，不限制今日头条。

## 工具身份硬门槛

- 头条页面的每一次观察和操作都必须来自 Computer Use 调用链：`mcp__node_repl__js` 中加载 `@oai/sky`，并通过 `sky.get_app_state`、`sky.click`、`sky.set_value`、`sky.type_text`、`sky.press_key`、`sky.scroll` 等 `sky.*` 方法控制真实前台 Chrome。
- 工具输出写着 `App: Google Chrome` 只表示 Computer Use 当前控制的 macOS 应用是 Chrome，**不代表使用了 Chrome 插件**。是否合规以工具调用名和调用链为准。
- 若调用记录出现 Chrome/browser 专用工具、Browser/Playwright、CDP、DOM 或后台 tab 对象，立即停止；这些结果不得作为头条页面证据，也不得与 Computer Use 结果混用。
- 本地文件读取、结果 JSON 写入和包校验可以使用文件/终端工具，但它们不得观察、推断或操作头条网页状态。

## 发布授权：明确指令即确认

- 用户在本人消息中明确说“发头条”“发布头条”“头条定时发布”，或给出“头条明天 7:30 发布”这类目的地、发布方式和时间明确的指令时，该指令本身就是本次头条发布的确认和授权。
- 同一内容、同一头条账号、同一发布时间的流程里，不得在填写标题、粘贴正文、进入预览、点击最终发布或定时发布前再次询问“是否确认发布”“要不要继续”或同义问题；用户补充“不要反复确认”时必须直接执行。
- 只有在会实质改变用户授权的目标、内容、账号、发布时间或可见范围仍缺失或发生变化时，才询问对应缺口。不要把内部状态机的 `TIME_CONFIRMED` 误解为需要再次向用户口头确认；它指的是程序读取并核对页面上的绝对时间。
- CAPTCHA、登录失效、平台强制管理员确认、安全交接或其他无法代办的硬阻断，按相应规则停下；这些不构成普通发布的重复确认。

## 权威内容

- 以用户确认的最终 Markdown/工作台正文为准，不从旧头条草稿反向覆盖本地稿。
- 标题使用用户指定的最终标题。正文不要重复插入文章标题、公众号原创篇号或微信专属签名。
- 当公众号标题已经确定、仅因头条 30 字限制需要缩短时，默认只给出并使用独立的头条短标题，不改 Markdown 总标题、公众号标题或已有公众号草稿；只有用户明确要求跨平台统一标题时才同步修改。
- 来源名称可以保留为纯文本，但正文不得包含任何外网超链接；发布前必须确认正文中的外部 `href` 数量为 0。
- 复制前检查首段、关键句、末段、后记和预期图片数。

## 不可跳过的执行顺序

在第一次填写或点击头条页面前，先完整读完本文件，并从用户请求中记录：最终标题、投放方式、封面模式、是否首发、发布方式、北京时间和预期图片数。用户未指定投放方式时，记录为默认值 `投放广告赚收益`。时间表达缺少具体小时或分钟时，先完成草稿准备，但必须在最终提交前向用户确认；不要替用户猜时间。如果用户已经把日期、小时和分钟说清楚，不得再次确认。

工作台的“选择头条格式 → 点击 `复制为头条格式`”是已有工作台文章进入头条的唯一正文入口。工作台从 Markdown 语义 DOM 直接生成头条版本：移除文章总标题、公众号原创篇号和微信签名，移除所有外部链接，把正文各级小标题统一为原生 `h1`，并保留图片的原始位置。不得从已经被微信排版扁平化为段落的 HTML 二次转换。

头条复制使用工作台按钮触发浏览器原生选区复制，把结构化 `text/html` 与纯文本表示一起写入 macOS 系统剪贴板。带图文章必须先通过公众号官方 API 创建草稿；成功回执中的正文图片 HTTPS 托管地址会按原顺序自动回填工作台。选择或复制头条格式时，工作台会从磁盘版本重新读取这批地址。复制前检查若发现托管图缺失或数量不等，会在写入剪贴板前阻断。

必须通过 Computer Use 在真实 Chrome 前台完成以下动作：用地址栏打开工作台、选择“头条格式”、点击一次 `复制为头条格式`，再从最新的 Computer Use 可访问性树或截图中读取“已复制”状态与图片数量。随后仍在这个真实前台标签页里，用 `super+l` 打开头条发布地址，并通过 Computer Use 在正文区执行一次 `super+v`。不得用浏览器虚拟剪贴板替代，不得先重建纯文字正文，不得改走头条的单图上传按钮，也不得用浏览器自动化绕过本流程。

选择头条格式时即检查 Markdown 总标题的可见字符数。超过 30 字仍可复制正文，工作台也可以继续显示警告；此时使用独立的头条短标题，不要为消除警告而回写公众号标题。头条编辑器中的实际标题缩短到 30 字以内之前不得进入最终提交。

每次失败后都重新打开干净发布页。不要在旧稿、半成品或段落顺序不明的页面上继续修补；自动保存形成的失败草稿不得发布，也不要未经用户允许删除。

### 定时发布入口白名单

头条编辑器底部可能同时显示 `预览`、`定时发布`、`预览并发布` 三个相邻按钮。用户要求定时发布时，第一次进入定时流程只允许点击文字精确等于 `定时发布` 的按钮。

- `预览并发布` 和任何仅标为 `发布` 的按钮属于立即发布路径，定时任务中禁止点击；不能因为希望先查看预览就选择 `预览并发布`。
- 点击前必须从最新一次 Computer Use 状态中同时读取编辑器底部的全部发布按钮，明确排除 `预览并发布`，并确认 `定时发布` 在当前状态中唯一可定位。滚动、窗口置前、标签页切换或页面状态变化后，旧元素序号立即失效，必须重新读取。
- 如果无法同时看清这些相邻按钮、`定时发布` 不唯一，或按钮层级与预期不一致，停止写操作并报告界面状态；不得按位置猜测、使用坐标点击或改点 `预览并发布`。

定时发布必须留下下面这条连续证据链，任一证据缺失都不得继续：

1. 最新 Computer Use 状态或截图同时看见 `预览`、`定时发布`、`预览并发布`。
2. 第一次进入定时流程时，只点击其中精确文字为 `定时发布` 的入口；不得点击 `预览并发布`。
3. 点击入口后立即重新读取 Computer Use 状态并查看截图。必须看到定时对话框和发布时间输入区域；可访问性树不完整时以 Computer Use 截图补证。看不到就停止，不能继续点击另一个同名按钮。
4. 设置日期、小时和分钟后，再用 Computer Use 逐字符读取完整北京时间。未读到与用户要求完全一致的绝对时间，不得进入预览。
5. 对话框中只点击一次 `预览并定时发布`；最终预览中只点击一次 `定时发布`，随后冻结所有写操作。
6. 管理页随后显示 `审核中` 是定时稿的正常中间状态，不能据此认定为立即发布、失败或错误时间，更不能因此删除或重发。

## Computer Use 前台硬门槛

Computer Use 操作的对象必须始终是 macOS 中真实、可见、最前方的 Google Chrome。整个头条流程不得同时创建或控制任何 Browser/Playwright 标签页；这样可以从根源上避免“后台自动化 tab 已到头条，但系统前台还在本地工作台”的错位。

从工作台复制到头条粘贴必须采用同一个真实前台标签页：

1. 先用 Computer Use 的 `sky.get_app_state({app:"com.google.Chrome"})` 读取真实 Chrome，基于最新可访问性树定位元素；不得使用旧 `element_index`。
2. 用 Computer Use 在该前台标签页打开工作台，选择“头条格式”，点击唯一一次复制按钮，并在最新状态中取得“已复制……N 张图片”的可见证据。
3. 通过 Computer Use 向同一 Chrome 发送 `super+l`，输入 `https://mp.toutiao.com/profile_v4/graphic/publish` 并回车。不要新建后台标签页。
4. 重新读取 Computer Use 状态，确认页面可见标题为头条发布页、账号已登录、页面是干净发布页；再填写标题并点击可见的正文编辑区。
5. 正文获得真实系统焦点后，Computer Use 只发送一次 `super+v`。随后仍只用 Computer Use 的最新状态和截图核验正文、图片、标题及平台计数，不得切回浏览器自动化。

如果 Computer Use 返回 `Computer Use is not allowed on the current browser URL`，按工具要求立即停止，不得换用 Browser/Playwright 绕过安全检查。用户恢复任务后，从真实 Chrome 的干净发布页重新开始；不得沿用失败页或提交它自动保存的半成品草稿。

## Computer Use 操作路径

1. 完整读取 Computer Use skill，只初始化 Computer Use，不初始化 Browser/Chrome browser-control skill。
2. 用 Computer Use 复用真实 Chrome 登录态，在同一前台标签页完成“工作台复制 → 地址栏导航到头条发布页”。
3. 通过最新可访问性树定位标题框和正文区；填写标题、点击正文区并执行一次 macOS 系统粘贴，一次性粘贴完整富文本与图片。
4. 继续只用 Computer Use 设置封面、广告、声明等发布选项。跨平台同步默认关闭 `头条首发`；只有用户确认满足平台当前独家/时限规则时才启用。
5. 用户只要求同步草稿时，止于保存草稿。用户明确要求直接发布或定时发布时，必须先通过“提交前硬门槛”，再进入预览和最终提交。
6. 立即发布时，用 Computer Use 在作品管理页等待状态从 `审核中` 变为 `已发布`。定时发布最终提交后，管理页可能先只显示 `审核中` 和提交时间；只要此前已经由 Computer Use 完整验证定时入口、绝对时间和最终 `定时发布` 按钮，就把它记录为正常中间状态，不删除、不撤回、不重投。若审核后出现 `将于 MM-DD HH:mm 发布`，再核对其与预期时间一致。
7. 立即发布后用 Computer Use 打开标题对应的公开链接验收。定时任务只有在用户要求继续监控时，才等待发布时间并做公开页验收。

## 定时发布状态机

头条会在不同阶段重复显示同名的 `定时发布` 按钮。按钮文字不能证明当前阶段；每次转换后都用 Computer Use 重新读取最新可访问性树并在需要时查看截图，以对话框、绝对时间和作品管理行作为唯一状态证据。禁止依赖固定等待时间、旧状态、旧元素序号或“再点一次试试”推进流程。

严格按下面五个状态执行，不得合并步骤：

1. `EDITOR_READY`：正文硬门槛全部通过。先在作品管理页检查当天是否已有同标题的 `审核中`、`定时发布中`、`已发布` 或 `仅我可见` 记录；只要存在就停止并向用户说明，不新建第二篇。
2. `TIME_DIALOG`：先通过“定时发布入口白名单”确认并排除 `预览并发布`，再通过 Computer Use 在编辑器底部点击一次文字精确等于 `定时发布` 的按钮。随后重新取状态，等待标题为 `定时发布` 的对话框和可见的发布时间输入区域。预览画面、加载中的禁用按钮或另一个同名按钮都不是下一步入口。时间对话框未出现时停止，不再点击任何发布按钮。
3. `TIME_CONFIRMED`：通过 Computer Use 设置日期、小时和分钟，再从最新可访问性树或截图读取完整北京时间，确认与用户要求逐字符一致，并把该字符串保存到本次结果记录。只有这时才能点击一次对话框里的 `预览并定时发布`。
4. `FINAL_PREVIEW`：等待最终预览完成，重新确认本次保存的绝对时间仍是预期值，再点击一次最终预览页的 `定时发布`。点击瞬间设置 `submission_maybe_sent=true`；本次任务的最终提交额度随即耗尽。
5. `MANAGEMENT_VERIFY`：只进行只读核验，等待进入作品管理页。同日同标题只能有一条有效记录，记录其 `pgc_id` 和状态。若该行先显示 `审核中`，将其视为定时稿的正常审核阶段；行内时间可能是提交时间，不得据此反推为立即发布。若审核后显示 `将于 MM-DD HH:mm 发布`，再核对它与保存过的绝对时间一致。不得仅因管理页暂未显示计划时间而删除、撤回或重投。

若最终点击后没有跳转、页面超时、连接中断或结果不明确，先到作品管理页按精确标题检查；绝对禁止再次点击最终按钮。查不到明确结果时停止并报告“提交结果未知”，不要重投。

结果记录必须保存这组可审计字段：`ui_driver: computer-use/@oai/sky`、入口前看到的全部发布按钮、`schedule_entry_clicked: 定时发布`、用户要求的绝对时间、Computer Use 实际读回的绝对时间、最终按钮文字、`submission_maybe_sent`、`pgc_id` 和管理页状态。这样可以从结果文件区分 Computer Use 与 Chrome 插件，也能证明走的是定时而不是立即发布路径。

## 单次提交熔断与一次性恢复

- 正常发布路径每篇文章每次任务最多执行一次可能产生作品记录的最终提交。点击前设置 `submission_maybe_sent=true`；重载页面、换标签页或打开干净发布页都不能把它重置为 `false`。
- 一旦 `submission_maybe_sent=true`，先冻结所有写操作，只到作品管理页和公开页做只读核验。若结果未知，先按精确标题、时间和 `pgc_id` 查明；不能把超时或未跳转当成“没有提交”。
- 如果作品管理页出现错误时间、意外立即发布、重复标题、正文截断或其他已证实的错误，记录每条相关作品的精确标题、`pgc_id`、时间、状态、展现和阅读数据。没有用户明确恢复授权时不得隐藏、删除、撤回、再次发布或另建同标题文章。
- 用户明确授权“删掉重发”后，每篇文章每次任务最多执行一次恢复事务。恢复预算字段为 `recovery_attempts_used`，初始值为 `0`；在第一次删除或其他恢复写操作之前先持久化为 `1`。重载页面、换标签页、浏览器重启或新开任务页面都不能重置该预算。
- 恢复时必须用精确标题、状态和 `pgc_id` 锁定错误行，只删除这一行，并回到作品管理页确认该 `pgc_id` 已消失。随后重新统计精确标题：如果正确的定时稿或已发布稿已经存在，清理到此结束，禁止再发；只有不存在正确作品时，才能在干净发布页重新跑完除正常提交锁以外的全部硬门槛，并最多执行一次替代稿最终提交。此时用恢复提交锁代替正常提交锁。
- 替代稿最终点击前设置 `recovery_submission_maybe_sent=true`。删除结果不明确、替代稿提交失败或未知、仍有重复行，或本次恢复开始前 `recovery_attempts_used` 已为 `1` 时，一律停止并报告；禁止第二次删除重发，也禁止用“再试一次”绕过预算。
- 结果文件必须记录 `recovery_attempts_used`、被删作品的 `pgc_id`、`deletion_verified`、替代稿 `pgc_id`（若有）以及 `replacement_submitted`。最终验收必须确保精确标题只剩一条有效记录；存在两条或以上时判定为失败并完整报告。

## 富文本与图片

通过 Computer Use 在工作台选择“头条格式”，从真实 Chrome 画面确认标题统一、微信专属元素移除和图片位置，并确认复制前检查显示可一键复制。通过 Computer Use 点击一次 `复制为头条格式`，并从最新状态确认页面显示已复制及预期图片数；再用 Computer Use 把同一前台标签页导航到头条页面，点击正文编辑区并执行一次 `super+v`。必须保留全部图片、单级标题、列表、加粗和原始顺序。正常同步不允许逐段恢复标题或逐图补传。

不要读取或拼装浏览器虚拟剪贴板，不要把页面 `execCommand('copy')` 的返回值单独当成成功。不要在 macOS 上误用 `ctrl+a` / `ctrl+v`；全选和粘贴使用 Computer Use 的 `super+a` / `super+v`。执行一次 `super+v` 后进入 `PASTE_PENDING`：带图富文本可能先显示 0 字，再异步出现正文和图片。最多等待 15 秒，期间只通过 Computer Use 做只读状态与截图核验，不得再次粘贴。只有等待结束后正文仍为空，才判定粘贴失败并保留现场；一旦出现正文，就用首段、末段、标题序列、可见图片块和平台字数作为验收证据。验收标准是：系统剪贴板中的完整富文本已经实际粘贴进头条编辑器，并通过下方硬门槛。

如果工作台提示托管图片缺失或数量不等，先停止并重新完成微信草稿上传/工作台回填；不要把 loopback 地址当成可交付图片。若单次系统粘贴失败，保留该干净页作为诊断现场并停止提交，报告准确错误，不自行改换正文导入方式或在目标编辑器中逐项修补。

图片进入编辑器后应被上传为头条图片。验收时以工作台已复制的预期图片数为基准，通过 Computer Use 逐屏检查正文中的可见图片块、第一张图和尾图；不要用 DOM、网络请求或后台页面脚本计数。

## 提交前硬门槛

以下条件必须全部成立，才能点击预览、立即发布或定时发布：

- 标题与用户指定标题完全一致、可见字符数不超过 30，正文没有重复标题、公众号篇号或微信签名。
- 工作台头条适配器的复制前检查已移除外部链接；头条编辑器中不得出现意外的链接卡片或可见外链。
- 首段、至少两个正文哨兵句和末段存在；标题文字及顺序与最终稿完全一致。
- Computer Use 逐屏核验的可见图片块与工作台复制状态中的预期图片数一致，第一张和尾图都在正确位置。
- 封面模式、广告、合集和作品声明符合用户请求；用户未明确要求不挂广告时，`投放广告赚收益` 必须处于选中状态；跨平台同步的 `头条首发` 保持关闭，除非用户明确确认符合规则。
- 定时发布必须显示完整的北京时间绝对值，并与用户确认的日期、小时和分钟完全一致。
- 正常提交时 `submission_maybe_sent` 必须仍为 `false`；一次性恢复提交时必须同时满足用户已授权、`recovery_attempts_used=1` 且 `recovery_submission_maybe_sent=false`。两种路径都要求当天作品管理页不存在同标题有效记录。

任一条件不成立都禁止提交。不要把“内容已经大致出现”“草稿已自动保存”或“平台没有报错”当成通过。

## 标题层级

工作台的“头条格式”预览与复制共用同一个版本化语义适配器，会主动把 Markdown `##` 到 `######` 统一转换为头条单级大标题。头条编辑器和公开页仍可能继续归一化样式；只要 Computer Use 看到的标题文字、顺序和视觉分隔正确，不要通过页面脚本或 DOM 注入强行恢复层级。

## 封面和声明

- 发布头条图文时必须主动完成封面选择。除非用户另有指定，默认选择“单图”，并选用正文第一张图片作为封面；不要只依赖平台自动选择。
- 选择后检查封面缩略图确实出现，并确认缩略图与正文第一张图片一致，再进入预览或发布。
- 不要把“正文已有题图”和“单图封面”误判为重复正文图片。
- 跨平台同步默认关闭 `头条首发`。该选项涉及平台时限和独家声明，不能仅因为按钮默认勾选就保留。
- 头条图文默认选择 `投放广告赚收益`。只有用户明确要求不挂广告时，才选择 `不投放广告`；不要把“去除微信正文里的广告卡片”误解为关闭头条广告收益。
- 不依赖页面初始状态或标签序号。按可见文本定位广告选项，并读取对应单选框的实际 `checked` 状态；若目标选项未选中，主动点击后再次验证。两个广告选项都未选中时，不得保存草稿或提交。
- 每篇头条结果文件和同步日志都记录 `toutiao_ads_enabled: true|false`；默认应为 `true`。合集未指定时保持账号默认值。

## 发布后验收

作品管理页出现正确标题且状态为 `已发布` 后，打开标题链接。公开页必须满足：

- 标题与用户最终标题完全一致。
- 首段、至少两个正文哨兵句、末段和后记都存在。
- 正文包含预期图片数；通过 Computer Use 逐屏检查可见图片块，不使用 DOM 或页面脚本取地址。
- 头条公开页使用懒加载。通过 Computer Use 逐屏向下滚动，确认每张正文图片实际显示且不是空白占位。
- 最末尾的尾图和后记可见，正文没有截断或段落错序。

若页面有问题，优先从作品管理页修改并重新验收；只有用户已授权且修改不可恢复时才删除重发。遇到 CAPTCHA 时停下并请求用户处理或授权。
