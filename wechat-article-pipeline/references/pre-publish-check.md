# 发布前隐藏检查记录

本规则用于 Agent 的发布工作流，统一覆盖微信草稿导入、头条/小红书草稿与立即或定时发布、三平台同步。它不改变发布授权，也不在正文、工作台、签名或原创篇号中显示计数。直接绕过 Skill 调用底层 API 脚本不会执行本提示。

## 发布前

1. 先取得工作台最新已保存的 Markdown，运行：

   ```bash
   python3 <skill>/scripts/article_check_state.py status <workspace>/files/<slug>.md
   ```

2. `current_check_count >= 1` 表示当前版本做过至少一次全文或完整语言检查。继续既有发布流程；检查过不等于没有问题，仍须阅读对应报告、说明未解决的重要问题或事实核查限制。技术包校验、复制前检查、仅核实数字、图片检查、写作差异复盘均不能替代语言检查。
3. `needs_check: true` 时，在任何平台写入前提示：**“当前文章还没有执行过检查，需要先检查再发布吗？也可以选择本次跳过检查，直接发布。”** 若累计计数大于零则改为：**“这篇文章检查后又有修改，当前版本还没有检查，需要先检查再发布吗？”** 说明这是本 Skill 的发布前检查提醒，引用本文件；等待选择，不擅自跳过。状态丢失、损坏或无法读取时也不能视为已检查，应说明原因并给出相同选择。
4. 用户选择先检查：按 [article-check.md](article-check.md) 检查并保存报告、登记计数。检查本身不授权改稿；仅按已有授权修改。若改稿，通读修订终稿并生成对应报告再登记。没有待用户决定的内容问题时继续原已授权发布，不再问一次发布确认。用户已经说“检查后发”时直接检查；已经明确说“这次不检查，直接发”时直接继续。
5. 用户选择跳过：仅对本次发布流程、同篇同版本生效，三平台共用这次选择，不递增检查计数、不伪造报告、不保存永久豁免。正文再次变化或新一轮发布需要重新判断。已检查版本跨会话可复用，不重复询问。
6. 交付内容在提示后有变化时，重新运行 `status`。定时发布在提交定时任务之前执行此规则。人工粘贴且无本地稿的文章先保存为明确的 Markdown 来源再登记，不能凭历史报告文件名猜测已检查。

## 检查完成后

检查开始先运行 `status` 并保留其 `article_sha256`；实际完成阅读和报告后才登记：

```bash
python3 <skill>/scripts/article_check_state.py record <workspace>/files/<slug>.md \
  --expected-sha256 <检查开始时的article_sha256> \
  --report <workspace>/files/<slug>.check.md --scope full
```

- 默认五项检查用 `full`；覆盖全文错别字、语法、病句、标点的语言检查用 `language`；仅查错别字、事实、局部段落等用 `other`，保留记录但不满足发布前语言检查要求。不得擅自扩大用户指定的检查范围。
- 检查过程稿件变化会拒绝登记；不能仅对新稿计算哈希来冒充已经读过。检查并修改后应重新通读最终版本，保存该版本报告，然后登记。
- 隐藏状态保存在 `files/.article-checks/<slug>.md.json`，累计次数与当前正文 SHA-256 的有效次数分开。报告路径与哈希也需匹配；报告删除或被改写后旧记录不再放行。同一报告重复登记不会重复计数。
- 历史报告默认不补记。只有核实报告确实记录当前正文哈希、范围包括全文语言检查且实际完成，才可登记；不能仅因存在 `.check.md` 便增加计数。
- 此脚本只保存检查证据，不会自动识别语法或判断报告质量；必须由 Agent 实际执行检查。不要在文章包 JSON 或 HTML 添加可见开关，也不要修改 `.env` 或原创篇号。
