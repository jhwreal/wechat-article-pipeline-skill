# 工作台光标—预览同步设计

## 背景与根因

Markdown 工作台当前在左侧输入后，会重新渲染右侧预览，再根据左侧 `scrollTop` 推算第一条可见 Markdown 行。它没有读取 `selectionStart`，因此用户在左侧视口底部修改内容时，右侧仍锚定左侧视口顶部对应的旧段落。

## 目标

- 用户输入、点击或用键盘移动光标后，右侧预览跟随光标所在 Markdown 行。
- 对应内容在自然滚动范围内尽量靠近右侧预览顶部，方便即时检查排版效果。
- 左侧纯滚动仍按左侧第一条可见行同步，右侧纯滚动仍保留现有反向同步。
- 不增加文章末尾的人造滚动留白，保持左右两栏自然的内容密度与视觉关系。
- 不改变 Markdown 渲染、公众号复制内容和文章排版。

## 交互规则

1. **输入文字**：重新渲染后，以折叠光标所在行为同步锚点。
2. **点击或键盘移动光标**：即使正文没有变化，也立即以新光标行同步右侧。
3. **左侧手动滚动**：以左侧顶部可见行同步右侧，不让屏幕外的旧光标把预览拉回去。
4. **右侧手动滚动**：保留现有右侧到左侧的反向同步。
5. **文章末尾**：目标位置超过右侧最大滚动距离时，钳制到自然滚动底部；不添加额外空白，因此最后一段不保证严格置顶。
6. **文本选区**：根据 `selectionDirection` 选择活动端；向后选择使用 `selectionStart`，其余情况使用 `selectionEnd`。

## 实现设计

在工作台模板的同步层增加两个独立的行号来源：

- `getCaretLine()`：根据折叠光标或选区活动端之前的换行数量计算光标行。
- 现有可见首行计算：继续根据 `editor.scrollTop / lineHeight` 计算，仅供左侧 `scroll` 事件使用。

同步入口明确区分意图：

- `input` 和光标/选区变化事件调用“按光标同步”。
- 左侧 `scroll` 事件调用“按视口同步”。
- 右侧 `scroll` 事件继续调用现有反向同步。

预览仍使用现有 `data-source-line` 块映射和 `findPreviewScrollForLine()`。渲染完成后的同步继续放在 `requestAnimationFrame` 中，确保 DOM 尺寸已经更新。现有滚动锁继续阻止双向事件互相触发形成循环。

为避免一次用户动作被多个光标事件重复执行，同一动画帧内的光标同步合并为一次；不引入新的持久状态或配置项。

## 测试与验收

先增加失败测试，再修改模板：

- 模板包含从 `selectionStart` 计算光标行的逻辑。
- 输入后的渲染同步明确使用光标行，而不是左侧 `scrollTop`。
- 左侧滚动仍明确使用顶部可见行。
- 点击和键盘光标移动能够触发光标同步。
- 右侧反向同步与滚动锁仍保留。
- 模板不包含末尾占位、动态底部留白等方案 C 行为。

使用截图对应的 `chatgpt-eats-codex-work-sites.html` 重新生成测试副本，在浏览器中验证：

1. 把光标点到左侧视口底部段落，右侧跳到对应内容。
2. 修改最后一句，右侧滚到自然底部并显示修改结果。
3. 用方向键跨行移动，右侧锚点随之变化。
4. 单独滚动左侧和右侧，原有双向同步仍正常且不抖动。
5. 复制富文本结果不包含任何同步辅助元素或额外空白。
